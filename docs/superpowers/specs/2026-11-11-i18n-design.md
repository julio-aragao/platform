# Full i18n, English-only code: design

Date: 2026-11-11. Status: draft for approval.

## Intent

Aurora Platform should speak the language of whoever opens it. Today every user-facing string, page route and message is hard-written in Portuguese, and Portuguese leaks into identifiers too. The goal is twofold:

1. **The product is fully internationalised.** Text, messages, and page URLs switch with the user's language. A Portuguese speaker and an English speaker who open the landing page on the same day each get a complete, natural experience in their own language, including the address in the browser bar.
2. **The code is English.** Portuguese exists only as translation data (including the Portuguese URL slugs). No Portuguese in identifiers, file names, CSS, comments, tests or docs.

pt-BR stays the default language of the product. English becomes the language of the codebase and the second supported language.

## Goals

- Two supported languages at launch: **pt-BR** (default) and **en**. Adding a third language means adding translation data and a route-name entry, with no code changes.
- Every user-visible string comes from translation data: page text, form labels and placeholders, button text, page titles and meta descriptions, ARIA labels, validation messages, auth error messages and API error messages.
- Page routes are English internally and localised in the URL: for example `/en/sign-in` and `/pt-br/entrar` are the same page. All internal links are generated from route names, never from literal paths.
- A visitor with no language in the URL lands on the right language (see Language selection).
- A visible language switcher on every page (landing, sign-in, sign-up, dashboard). Switching keeps the user on the equivalent page in the other language, not on the home page.
- Numbers, dates and the footer revision line are formatted for the locale (for example `1.250 kWp` in pt-BR vs `1,250 kWp` in en, and each language's own date format).
- `<html lang>` matches the language being shown, and each page declares its alternate-language URLs (`hreflang`) so search engines link the versions.
- No flash of the wrong language: the first server-rendered response is already in the right language.

## Non-goals

- No third language now, no right-to-left support, no per-user language stored in the database. The remembered choice lives in a cookie only.
- No runtime or machine translation. Translations are written by hand and committed.
- Brand and company names ("Aurora", "Aurora Tecnologias") are not translated. The brand-kit logo artwork is unchanged.
- User-created data (names, future plant and document content) is not translated.
- No mobile app work. There is no mobile app in the repo yet; the shared pieces should be usable by it later.
- No change to the database schema.

## Anti-goals (a failure even if it technically works)

- Any user-visible string still hard-coded in a component or in an API response after this work.
- Two copies of the same text, schema or message map (one per app, or one per language file shape). Locales and message shapes are defined once.
- Components forked per language ("`HomePageEn`"). One component, many catalogs.
- English-only or Portuguese-only URLs surviving anywhere, including redirects (for example the dashboard redirecting to a Portuguese path while the user is on English).
- A translation file that silently falls back to the other language when a key is missing. Missing keys must fail a test or build, not render the wrong language quietly.

## Constraints

From the repository's own rules (`CLAUDE.md`), which apply to this work:

- Every API error keeps the `{error: {code, message}}` shape (Better Auth's `/api/auth/*` is the exception). `code` stays the stable thing apps rely on; `message` is localised.
- Each data shape is defined once as a Zod schema in `packages/shared`. Shared code must not hold Portuguese sentences; it holds keys and locale definitions.
- Dependencies pinned exactly; no `minimumReleaseAgeExclude` entries; Node 22.
- Dependency inversion: business logic does not read `process.env` or import singletons. The API receives locale handling through `createApp(deps)` style injection and stays testable without the network.
- Open/closed: new locales and new routes are added, not edited into `if/else` chains.
- Definition of done: `pnpm lint && pnpm typecheck && pnpm test && pnpm build` all pass.

## Decisions already made (as the product owner decided them)

- Two languages, en and pt-BR; pt-BR is the default; code and routes are English.
- Routes are translated per language.
- The language is the first segment of the URL. A first visit with no language in the URL goes to the language the browser asks for, or pt-BR if that is neither en nor pt-BR. A language switcher lets people change it.
- All Portuguese in code is renamed to English: routes, file and component names, CSS class names and colour tokens (for example `ficha-usina` to `plant-sheet`; `tinta`, `grafite`, `gelo` to English colour names).
- `DESIGN.md` is rewritten in English with the English token names. The Portuguese brand colour names are kept as a note so the brand document still lines up with the brand kit.
- API error messages follow the language of the request (via the standard `Accept-Language` header). Shared validation schemas return message keys; each app turns keys into text.

## Decisions made by me (the designer), for you to check

These are my calls, not agreed requirements.

1. **URL language segments are lowercase `/en` and `/pt-br`**, and the prefix is always present (no unprefixed default-language URLs). Always-prefixed URLs make the language unambiguous and avoid two URLs for one page.
2. **Route names and slugs.** Internal route names: `home`, `sign-in`, `sign-up`, `dashboard`. English slugs: `/`, `/sign-in`, `/sign-up`, `/dashboard`. Portuguese slugs: `/`, `/entrar`, `/criar-conta`, `/painel`. These slugs live in the one route-map file and are counted as translation data, not as "Portuguese in code".
3. **Language resolution order:** language in the URL, then the remembered choice (cookie set when the user uses the switcher), then browser `Accept-Language`, then pt-BR.
4. **Where texts live.** Page and component copy lives with the web app, in one catalog per language. Shared pieces live in `packages/shared`: the supported-locale list and default, the translatable validation and error keys with their en and pt-BR texts, and the error-code-to-message catalog the API and the apps both use. Rule: if two apps could need it, it is in shared; if only the web page needs it, it stays in web.
5. **Better Auth errors** keep arriving as codes; the web app maps those codes to localised messages (as it does today), now from the catalog.
6. **API language comes from the request, and only from `Accept-Language`** (no cookie). The web app sends the language of the page the user is on, not the browser's language, on every call to the API, so the page and any API message always match. This covers both the server-side session lookup and the browser-side Better Auth client calls, which today go straight through the `/api` rewrite with the browser's own header. The builder must make the browser-side client send the page language (for example through a custom fetch or header in the auth client).
7. **Sample content on the landing page** ("Usina Solar Exemplo I", "Exemplo Energia", the example caption) is translatable copy. The `CNPJ` label and the example CNPJ number stay as they are in both languages, because they are a Brazilian company identifier.
8. **Brand-kit asset file names** referenced by code (`Aurora_Marca-Reduzida.svg` and the negative version) are renamed to English file names in the app's `public/` folder. The kit's original files outside the repo are untouched.
9. **A guard against regressions:** a cheap automated check that fails when translation catalogs differ in keys between languages, and when source files outside catalogs contain Portuguese words or accented text. The exact rule is the builder's choice; it should avoid false alarms on legitimate content.

10. **Paths outside the language routing.** `/api/*`, `/_next/*`, fonts, brand images, the favicon and other static files are never prefixed and never redirected.
11. **Redirect rules.** An unprefixed page URL (for example `/`) redirects temporarily (307) to the right language, because the target depends on the visitor. The old Portuguese-only URLs (`/entrar`, `/criar-conta`, `/painel`) redirect permanently (308) to the localised URL. They use the language resolution order from decision 3, not always pt-BR.
12. **Validation errors.** Shared Zod schemas carry message keys. Web forms turn keys into text from the shared catalog, using the page language. API validation errors (400) are translated by the API from the same catalog, in the request language, inside the `{error: {code, message}}` shape.
13. **Locale-aware redirects and links.** Server redirects (the dashboard sending a signed-out visitor to sign-in, sign-in and sign-up sending a signed-in visitor to the dashboard, and the redirect after a successful sign-in) all go through one helper that builds the localised URL for the current language.
14. **Cookie.** The language cookie is a functional preference with a one-year lifetime, `SameSite=Lax`, `Secure` in production, and is not used for anything else. I assumed it needs no consent banner; the product owner should confirm that with whoever handles privacy for the platform.
15. **Exempt from the Portuguese guard:** applied Prisma migrations (never edited, per `CLAUDE.md`), the translation catalogs, the route-map slugs, and the Portuguese brand-colour note in `DESIGN.md`.

## What is left to the builder

- Choosing the i18n library (likely `next-intl` for the web app, if it supports the pinned Next 16 and can be pinned exactly under the repo's release-age rule; otherwise the closest equivalent) and the mechanism for localised pathnames and the language redirect.
- The exact catalog key naming and file layout, as long as the rules above hold.
- How the language switcher looks, following `DESIGN.md` (flat, no shadows, no rounding, Plex fonts). It must be keyboard-accessible and announce the language names in their own language ("English", "Português").
- The English colour-token names and CSS class names, and the English wording of every string, subject to review by the product owner.
- The exact shape of how the API receives and applies the request language, within the dependency-inversion rule.
- The order of work and how to split it into reviewable steps.

## Scope inventory (what exists today and must change)

- `apps/web`: landing page (`app/page.tsx`: hero, plant data sheet, three pillars, closing call to action, footer), sign-in and sign-up pages, dashboard page, all components, `layout.tsx` metadata and `lang`, `auth-messages.ts`, route folders `entrar`, `criar-conta`, `painel`, the `ficha-usina` component, `globals.css` colour tokens and class names (`barra`, `rotulo`, `dado`, `btn-primario`, `btn-secundario`).
- `packages/shared`: Portuguese messages inside the `auth` schemas; `errors` stays code-based.
- `apps/api`: Portuguese messages in `app.ts` (not found, internal error) and `routes/me.ts` (unauthorized).
- Tests: `apps/web/test/auth-messages.test.ts`, `apps/api/test/app.test.ts` and helpers assert Portuguese text and must be updated to the new behaviour, plus new tests for locale resolution, route generation, catalog parity, and localised API errors.
- Docs: `DESIGN.md`, `.env.example` if any new variable is introduced.

## Success looks like

- Opening `/` with an English browser lands on `/en` with English text, an English sign-in link pointing to `/en/sign-in`, and the page in English from the first byte.
- Opening `/pt-br` shows the same page in Portuguese with `/pt-br/entrar`.
- On `/pt-br/entrar` the switcher goes to `/en/sign-in`; a wrong-password attempt shows the error in the language of the page.
- Visiting the old Portuguese-only URLs (`/entrar`, `/criar-conta`, `/painel`) redirects to the right localised URL.
- A repo-wide search for Portuguese words outside translation data returns nothing, and `pnpm lint && pnpm typecheck && pnpm test && pnpm build` pass.
