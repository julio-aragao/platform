# Full i18n, English-only code: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the platform switchable between pt-BR and English (texts, messages, page URLs), with pt-BR as the default and an English-only codebase.

**Architecture:** `packages/shared` owns the locale list, language negotiation, the shared message catalogs (validation, API errors, auth errors) and a `translate` function. The API reads `Accept-Language` and localises every error. The web app uses `next-intl` with a locale-prefixed, localised-pathname route tree (`/en/sign-in`, `/pt-br/entrar`); our own `proxy.ts` handles language detection and legacy redirects, `next-intl` handles slug mapping.

**Tech Stack:** Next 16.4.6, next-intl 4.14.9 (pinned), Hono 4, Zod 4, Better Auth, Vitest 5.1.0, Tailwind 4.

**Spec:** `docs/superpowers/specs/2026-11-11-i18n-design.md`. Read it first; this plan only records the decisions the spec leaves open.

## Global Constraints

- Languages: `pt-br` (default) and `en`. URL segments are lowercase `/pt-br` and `/en`, always present (no unprefixed page URLs).
- Route names / slugs: `/` ; `/sign-in` = `/entrar` (pt-br); `/sign-up` = `/criar-conta`; `/dashboard` = `/painel`. These slugs live only in `apps/web/src/i18n/pathnames.ts`.
- Language order: URL, then `NEXT_LOCALE` cookie, then `Accept-Language`, then pt-br. Invalid cookie values are ignored.
- Cookie: `NEXT_LOCALE`, one year, `SameSite=Lax`, `Secure` in production, written only when the user uses the switcher.
- API takes language only from `Accept-Language`; the web app sends the page language on every API call (server-side and browser-side).
- Error responses keep the `{error: {code, message}}` shape; `message` is localised. `/api/*`, `/_next/*`, fonts, brand images, favicon and any path containing a dot are never prefixed or redirected.
- Redirects: unprefixed page URL is 307 to the resolved language; legacy URLs `/entrar`, `/criar-conta`, `/painel` are 308 to the localised URL in the resolved language. Query strings are preserved.
- No Portuguese anywhere except: `packages/shared/src/i18n/catalogs/**`, `apps/web/src/i18n/messages/**`, `apps/web/src/i18n/pathnames.ts`, applied Prisma migrations, the brand-name note in `DESIGN.md`, and `docs/superpowers/**`.
- Pin dependencies exactly. Do not add `minimumReleaseAgeExclude` entries to `pnpm-workspace.yaml`. Node 22.
- Brand and company names are not translated. The `CNPJ` label and the example CNPJ number stay as-is in both languages.
- Shared code holds keys and catalogs, never page copy. After changing `packages/shared`, run `pnpm --filter @aurora/shared build` before running `api` or `web` tests (they consume `dist`).
- End every commit message with the `Co-Authored-By` line from the session's attribution rule.
- Done means `pnpm lint && pnpm typecheck && pnpm test && pnpm build` all pass.

## Review Focus

Inputs the spec implies but its examples don't spell out. Each has a test in the task that owns the code.

1. Invalid or odd language signals: cookie `NEXT_LOCALE=fr`, `Accept-Language` that is empty, `*`, `q=0`, malformed or very long. Must fall back to pt-br, never throw. (Tasks 1, 6)
2. Query string must survive every redirect, e.g. `/entrar?next=%2Fpainel` in English goes to `/en/sign-in?next=%2Fpainel`. (Task 6)
3. A page URL with the other language's slug (`/pt-br/sign-in`) or a wrong-case prefix (`/EN/sign-in`) ends at the canonical localised URL, not a 404 or a mixed-language page. (Task 6)
4. API validation failures must never leak a raw English Zod message into a pt-br response; unknown messages become the generic bad-request message in the request language. (Tasks 2, 3)
5. Session lookup failing (API down, 401, bad JSON) is treated as signed out, and the redirect to sign-in stays in the page's language. (Task 7)

**Produces:**
```ts
export const LOCALES = ["pt-br", "en"] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale; // "pt-br"
export function isLocale(value: unknown): value is Locale;           // exact, case-sensitive
export function htmlLang(locale: Locale): string;                    // "pt-BR" | "en"
export function negotiateLocale(acceptLanguage: string | null | undefined): Locale;
export function resolveLocale(input: { cookie?: string | null; acceptLanguage?: string | null }): Locale;
```
Rules: `negotiateLocale` sorts by `q` descending (ties keep header order), drops `q=0`, matches by primary subtag (`en*` to `en`, `pt*` to `pt-br`), `*` and unknown tags are skipped, no match returns the default, headers over 1000 characters return the default, never throws. `resolveLocale` uses the cookie if `isLocale`, else `negotiateLocale`.

  - Defaults: `null`, `undefined`, `""`, `"*"`, `"fr"`, `"en;q=0"`, `";;;,,"`, `"x".repeat(2000)` all return `"pt-br"`.
  - `resolveLocale({ cookie: "en", acceptLanguage: "pt-BR" })` is `"en"`; `{ cookie: "fr", acceptLanguage: "en" }` is `"en"`; `{ cookie: "EN" }` falls through to the header/default (cookie matching is exact); `{}` is `"pt-br"`.

**Produces:** `export default function proxy(request: NextRequest): NextResponse` and `export const config = { matcher: ["/((?!api|_next|brand|.*\\..*).*)"] }` (Next 16 calls the file `proxy.ts`).

Proxy behaviour, in order:
1. First path segment lower-cased equals a locale and is not already exactly that locale (`/EN/...`): 307 to the lower-case version, query kept.
2. Path has no locale prefix and `legacyRedirectTarget(pathname)` is set: 308 to `getPathname({ locale: resolved, href })`, query kept. `resolved = resolveLocale({ cookie: NEXT_LOCALE cookie value, acceptLanguage })`.
3. Path has no locale prefix: 307 to `/${resolved}${pathname}` (`/` gives `/pt-br`, not `/pt-br/`), query kept.
4. Otherwise delegate to `createMiddleware(routing)` from `next-intl/middleware`.

Layout (`[locale]/layout.tsx`): `hasLocale(routing.locales, locale)` else `notFound()`; `setRequestLocale`; `<html lang={htmlLang(locale)}>`; fonts as today; `NextIntlClientProvider`; `generateStaticParams` over `routing.locales`; `generateMetadata` gives `title: { default: "Aurora", template: "%s · Aurora" }` and the localised description.
